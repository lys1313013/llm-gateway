# JWT 身份校验与密钥轮换

## 签名密钥必须显式配置

后端 HTTP 服务启动前校验 `JWT_SECRET_KEY`：不得为空、少于 32 字节、含首尾空白或使用已发布的默认值。推荐用 `openssl rand -hex 32` 生成独立随机值，通过受保护的环境配置注入，禁止提交或打印实际值。Compose 的变量现在必填，`.env.example` 不再提供可运行的公共密钥。`JWT_EXPIRATION_HOURS` 必须为 1～8760 小时。

`gateway -version`、`gateway migrate`、`gateway migrate -status` 不需要 JWT 密钥，不会因为只做版本/数据库运维而访问认证服务；使用整份 Compose 时仍须满足 Compose 的必填变量检查。HTTP 服务在建立数据库连接前拒绝不安全的 JWT 配置，JWT 签发及验证也独立拒绝同类配置。

## 每次请求使用当前账号状态

JWT 只接受 HS256，必须有到期时间、签发时间、匹配的主体和认证版本。API 每次请求从数据库加载当前用户，检查账号存在、启用状态及认证版本，再将当前用户角色和团队写入上下文。数据库读取失败会拒绝访问，不回退旧令牌权限。

认证版本是由服务器签名密钥对用户 ID、用户名、密码哈希、角色、团队、启用状态、创建/修改时间计算的 HMAC。令牌不包含密码哈希，也不包含可直接用于离线猜测密码的未加密哈希指纹。修改密码、角色或团队后旧 JWT 立即失效；删除/禁用账号后不能继续访问。改变角色后再恢复也不会恢复旧令牌，因为现有安全修改都会更新 `users.updated_at`。

此修复不增加数据库字段或迁移。当前登录和 API Key 使用时间更新不会更新 `users.updated_at`，正常重复登录不会使其他会话失效。以后若增加会更新此时间的非安全资料编辑，应评估是否允许注销其他会话，或改用专用且单调递增的认证版本。直接运维修改账号安全字段应同时更新 `updated_at`，以防恢复到旧状态时复活旧令牌。

旧版 JWT 没有认证版本，升级后统一要求重新登录。修改密码会使当前会话也失效。API Key 使用独立的数据库认证路径，其撤销策略未随 JWT 变化。

## 已部署默认密钥的处理

应先限制管理入口的暴露范围，再写入新的独立随机签名密钥并让服务重新加载；只改管理员登录密码无法修复默认签名密钥。新密钥使旧 JWT 全部失效，用户需重新登录。

检查异常管理操作和 API Key 暴露范围，按需要另行撤销 API Key。不要把旧默认签名密钥作为兼容密钥继续接受。备份只保存在受限目录，不在终端或工单中展示秘密。轮换、重启和生产验证是部署步骤，本文件不代表这些步骤已执行。

隔离回归包含：默认密钥拒绝、缺失到期/认证版本或非 HS256 令牌拒绝；账号删除/禁用/改密/降权/换团队后的旧令牌拒绝；角色恢复也不复活旧令牌；数据库不可用时拒绝；正常账号和重新登录后的令牌可用。
